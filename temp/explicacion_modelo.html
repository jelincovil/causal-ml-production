Seccion 1

El problema en una frase

Los supuestos que hacen valido un modelo causal no desaparecen cuando lo desplegamos. Un estimador entrenado hoy sigue siendo valido solo mientras la pregunta, el grafo causal, la definicion del tratamiento, la poblacion de entrada y el soporte estadistico sigan siendo compatibles con lo que se entreno. Este repositorio convierte esa condicion en un mecanismo ejecutable:

SUPUESTO→ CONTRATO→ CHECK→ GATE→ EVIDENCIA→ MONITORING→ DECISION

Es un servicio de machine learning causal con validez operacional: estima el efecto solo si los datos de entrada cumplen un contrato verificable. Si lo incumplen, bloquea; si hay condiciones dudosas, estima con advertencia; si todo pasa, estima. El repositorio entero (modelo, contrato, evidencia, perfil de referencia y CI) viaja junto con la app, de modo que cada estimacion es trazable a la version que la produjo.

Seccion 2

El modelo

2.1 Que se estima: el ATE

El estimando es el ATE (Average Treatment Effect), es decir E[Y(1) − Y(0)]: la diferencia media entre el resultado potencial bajo tratamiento y bajo control, sobre la poblacion. El tratamiento (treatment) es binario y el resultado (outcome) es continuo.

Bajo la especificacion usada (regresion parcialmente lineal), el efecto es homogeneo: no hay efecto individual (CATE). No sirve para focalizar subgrupos ni decisiones individuales.

2.2 Identificacion: el DAG y la puerta trasera

Para pasar de una correlacion a un efecto hace falta identificar el estimando. El contrato declara 25 covariables pre-tratamiento que son a la vez causa del tratamiento y del resultado (confusores observados). De esa declaracion se construye un grafo aciclico dirigido (DAG):

El ajuste se justifica con el criterio de puerta trasera de Pearl, que el codigo comprueba con NetworkX (nx.is_d_separator): el conjunto de ajuste no debe contener descendientes del tratamiento y debe d-separar T y Y al eliminar las aristas que salen de T. En la practica, ajustar por las 25 covariables bloquea todos los caminos de puerta trasera del DAG declarado. DoWhy confirma ademas, en el release, que el estimando es identificable a partir de ese grafo (estrategia backdoor).

El DAG no lo validan los datos. El codigo solo audita su coherencia interna (que las covariables, el schema y los nodos concuerden y que se cumpla la puerta trasera). Que la estructura causal sea la correcta exige justificacion sustantiva, no la comprueba la app.

2.3 El estimador: double machine learning (PLR)

Se usa econml.dml.LinearDML con X = None y las 25 covariables como controles W. Es una regresion parcialmente lineal (PLR) resuelta con double machine learning. La idea, en palabras llanas:

  1. Se aprende a predecir el resultado E[Y|X] y el tratamiento E[T|X] usando las covariables (nuisances), en este caso con LassoCV.
  2. Se toman los residuales fuera de muestra de ambas predicciones: la parte de Y y de T que las covariables no explican.
  3. El efecto es la relacion entre esos dos residuales. Al separar la estimacion de las nuisances se elimina el sesgo de regularizacion, que es el truco central del DML.

El cross-fitting con 5 folds (variante DML2: la etapa final usa todos los residuales fuera de muestra) evita el sobreajuste que ocurriria si se usaran los mismos datos para predecir y para estimar.

2.4 Dos estimaciones que no deben confundirse

Referencia

El ATE del modelo desplegado (causal_model.joblib), entrenado con data/dataset.csv. Es fijo: lo produce el release.

Reajustada sobre la entrada

El mismo estimador reajustado sobre los casos completos de los datos de entrada. Solo se ejecuta si la validacion no produjo BLOCK. La diferencia entre ambas es informacion, no una prueba.

Seccion 3

El entrenamiento

3.1 Quien entrena y donde

El entrenamiento ocurre offline, en el ciclo de release, no en la nube. En runtime la app solo carga el artefacto. El ciclo tiene tres pasos en un orden estricto:

python scripts/train_model.py                 # -> artifacts/model/
python scripts/generate_reference_profile.py  # -> artifacts/monitoring/
python scripts/validate_release.py            # -> artifacts/validation/ + model_card.json

3.2 train_model.py paso a paso

  1. Carga el contrato (causal_contract.yaml) y el dataset (data/dataset.csv, n = 1200).
  2. Ajusta el estimador con fit_effect_model: LinearDML con model_y y model_t = LassoCV(max_iter=5000, random_state=42), cv=5, sobre los casos completos.
  3. Resume la inferencia con ate_summary: ATE, error estandar e intervalo de confianza al 95% (ate_inference() de EconML).
  4. Construye los metadatos (build_metadata) y guarda el bundle joblib + el SHA-256 del artefacto.

3.3 Que se guarda: el artefacto y su huella

El artefacto es un pickle de EconML/scikit-learn: causal_model.joblib. Junto a el se guarda model_metadata.json, que fija la trazabilidad:

  • Versiones de contrato: tratamiento, preprocesamiento y DAG (todas 1.0.0).
  • Especificacion del estimador: metodo, nuisances, folds y semilla.
  • Hash de los datos (training_data_sha256) y hash del modelo (model_sha256).
  • Versiones de librerias al entrenar: Python 3.12.3, econml 0.17.0, scikit-learn 1.9.1, numpy 2.4.6, pandas 3.0.6.
Por que se fijan las versiones exactas. Un pickle es fragil: si scikit-learn o numpy cambian, la carga puede comportarse distinto o romperse. Por eso requirements.txt pinea esas versiones y validation/consistency_checks.py emite WARN si la version mayor.menor difiere de la del entrenamiento, y BLOCK si el hash del artefacto no coincide con el de los metadatos.

3.4 La prueba sintetica: el estimador se gana el derecho a usarse

Antes de publicar el release, validation/synthetic.py simula datos con un efecto verdadero conocido (tau = 2.0) bajo confusion observable y comprueba que el estimador lo recupera. El release exige un error absoluto ≤ 0.40; en la practica el error es ~0.033. Es una prueba de recuperacion: confirma que la maquinaria funciona cuando la respuesta es conocida.

Si el schema o el tratamiento son invalidos, las verificaciones que dependen de los datos se marcan SKIPPED. La decision final es binaria:

BLOCK  -> EFFECT ESTIMATION: BLOCKED   (st.stop(), no se calcula nada)
WARN   -> EFFECT ESTIMATION: ALLOWED con advertencias
PASS   -> EFFECT ESTIMATION: ALLOWED

4.3 Positividad (overlap)

La positividad exige que ninguna unidad tenga probabilidad de tratamiento cercana a 0 o a 1, porque sin contraste entre tratados y controles no hay efecto estimable. Se calcula el propensity score con una regresion logistica con cross-fitting estratificado de 5 folds (distinta del LassoCV del estimador: es una verificacion bajo esa especificacion). Se reportan minimo, maximo, cuantiles 1% y 99%, fraccion de observaciones fuera de la banda y el ESS/n de los pesos IPW de tratados y controles. En la poblacion de referencia el propensity esta en [0.11, 0.72], lejos de ambos umbrales.

4.4 Distribution shift: PSI y KS

La comparacion no se hace contra la nada: el perfil de referencia guarda, por covariable, media, desviacion, minimo, maximo, q01, q99, bordes y proporciones de deciles (para PSI), una malla de 101 cuantiles (para el KS aproximado) y la tasa de nulos, ademas de la tasa de tratamiento.

  • PSI por variable con los deciles de referencia: es la metrica que activa WARN.
  • KS aproximado: estadistico de una muestra contra la CDF de referencia reconstruida con la malla de cuantiles (informativo, pues no guarda la muestra completa).
  • Tasa de tratamiento: un cambio de asignacion es senal de cambio del mecanismo de seleccion aunque las covariables no se muevan.
El drift no bloquea. El contrato fija drift.action: warn: incluso en nivel critical, la app advierte pero estima. Bloquear la estimacion se reserva para dominio y nulos.

4.5 SUTVA: interferencia entre unidades

SUTVA supone que el resultado de una unidad no depende del tratamiento de otras. Si el contrato define una variable de agrupacion (cluster_column), validation/sutva_checks.py reporta el ICC del tratamiento y la saturacion por cluster como senal indirecta de derrames. Hoy el contrato la fija en null: sin esa variable no es evaluable, asi que aparece como NOT PROVABLE y exige justificacion sustantiva.

4.6 Sensibilidad a confusion no observada

validation/sensitivity_checks.py calcula el valor de robustez de Cinelli y Hazlett (2020): la fuerza minima (R2 parcial con T y con Y) que un confusor no observado necesitaria para anular la estimacion. Se calcula sobre la regresion de residuales del DML (t = ATE/SE, dof = n − p − 2). En la referencia: 27.0% (22.7% para que el IC incluya 0). Es una aproximacion, no una prueba de ignorabilidad.

4.7 Refutaciones (DoWhy)

causal_model/refutation.py identifica el estimando con el DAG (backdoor) y estima con backdoor.econml.dml.LinearDML. Corre tres refutadores con 50 simulaciones cada uno:

RefutadorQue haceResultado (release)
placebo_treatmentsustituye el tratamiento por uno falso; el efecto debe desaparecer PASS p ≈ 0.48
random_common_causeanade una causa comun aleatoria; el efecto no debe cambiar PASS p ≈ 0.35
data_subsetreestima sobre el 80% de los datos; el efecto debe ser estable PASS p ≈ 0.29

Un refutador pasa si su p-valor supera 0.05. El resultado se guarda en artifacts/validation/refutation_report.json y la app solo lo presenta: no lo recalcula sobre la entrada actual. Los tres refutadores estan marcados required en el contrato: si alguno falla, no hay release.

4.8 El catalogo de supuestos: 16 supuestos en tres niveles

La pantalla Supuestos del analisis separa lo que se contrasta con los datos de lo que no, incluidos los supuestos del metodo. Es una fuente unica (validation/assumptions.py): validate_release.py lo escribe en la seccion supuestos de la model card y la app lo renderiza sin texto propio. Solo informa: no cambia ningun veredicto ni los umbrales.

Nivel 1 · Verificados empiricamente con los datos (6)

Cada uno se contrasta con una funcion y un umbral en esta ejecucion.

  • Esquema de entrada conforme al contrato.
  • Tratamiento binario con ambos niveles.
  • Positividad (overlap).
  • Dominio de referencia: cada covariable cae en [q01, q99] del entrenamiento.
  • Estabilidad de la poblacion (drift / PSI).
  • Completitud: tasa de nulos bajo el umbral; la estimacion usa casos completos.

Nivel 2 · Evidencia indirecta (2)

No se pueden comprobar; hay una medida que los hace mas o menos plausibles. Nunca devuelven PASS por si solos.

  • Ignorabilidad condicional (sin confusion no observada): valor de robustez.
  • Efecto no espurio y estable: refutaciones de DoWhy.

Nivel 3 · No verificables por la aplicacion (8)

La app los supone o los declara, pero no los comprueba: requieren justificacion sustantiva.

  • Estructura causal (DAG) correcta.
  • SUTVA (sin interferencia).
  • Consistencia de la definicion del tratamiento.
  • Identificacion valida en la poblacion de entrada.
  • Datos faltantes ignorables (casos completos).
  • Homogeneidad del efecto (PLR con X=None): la app no contrasta heterogeneidad.
  • Nuisances bien estimadas (LassoCV, sin diagnostico de convergencia).
  • Normalidad asintotica del IC 95%.

Seccion 5

La puesta en produccion

5.1 La arquitectura

Hay tres entornos con responsabilidades distintas. Lo offline produce evidencia; lo cloud solo valida, decide y estima con lo que ya viaja en el repositorio.

Offline (release)

Entrena y produce evidencia.

  • Entrena LinearDML y guarda el artefacto + SHA-256.
  • DoWhy corre las refutaciones (50 simulaciones) y las guarda en JSON.
  • Sensibilidad, prueba sintetica y model card.
  • Genera el perfil de referencia (cuantiles, deciles, tasas).

Runtime (cloud)

Solo carga y presenta; valida cada entrada.

  • Carga contrato, modelo, perfil y evidencia del repositorio.
  • Presenta el JSON de refutaciones; no las recalcula.
  • Compara la entrada contra el perfil (PSI, KS, dominio, nulos).
  • Estima (PASS/WARN) o llama a st.stop() (BLOCK).

5.2 Decisiones de diseno que la nube hace necesarias

  • El repositorio es el release. Streamlit Community Cloud despliega lo que hay en GitHub; por eso modelo, contrato, perfil de referencia y evidencia estan versionados en artifacts/ y contracts/.
  • Versiones exactas. Un cambio en requirements.txt provoca un redeploy completo; las versiones pinneadas protegen el pickle. El CI comprueba la integridad del artefacto.
  • La nube no garantiza disco. El disco local no es persistente, asi que no se usa un CSV local como historial. Con [history].url en st.secrets el historial va a una base SQL externa; sin eso vive solo en la sesion.
  • La cache no es la validacion. st.cache_resource solo evita recargar contrato, modelo y perfil; la validez la protege el contrato, que se evalua en cada ejecucion.
  • Sin configuracion peligrosa. .streamlit/config.toml solo define el tema (CORS y XSRF quedan en sus valores por defecto). No hay packages.txt: ninguna dependencia necesita paquetes del sistema.
  • Falla rapido y no sobrescribe. Si los datos o artefactos son inconsistentes, validate_release.py sale con exit 1 en segundos, sin reemplazar la evidencia anterior.

5.3 Monitoring e historial

poblacion de referencia -> reference_profile.json -> nueva poblacion -> monitoring/drift.py -> comparacion

El boton Guardar esta evaluacion en el historial registra fecha, version del modelo, estado, n, PSI maximo, KS maximo, tasa de tratamiento y ATE reajustado. Para que la afirmacion monitorizamos la degradacion en produccion sea cierta hace falta persistencia externa:

[history]
url = "postgresql+psycopg2://usuario:clave@host:5432/base"

Con PostgreSQL hay que agregar el driver (por ejemplo psycopg2-binary) a requirements.txt. Sin [history] la app usa el historial de sesion y lo avisa.

5.5 El flujo de la app en runtime

INPUT→ VALIDATE→ DECIDE→ ESTIMATE→ REPORT
  1. Entrada: un escenario de demostracion o un CSV propio (columnas del feature_schema.json).
  2. Estado de validez causal: las 11 verificaciones y la decision ALLOWED / BLOCKED.
  3. Supuestos del analisis: los 16 supuestos en tres niveles (se muestran siempre, tambien con BLOCK).
  4. Decision: si hay BLOCK, mensaje y st.stop(); si hay WARN, aviso y continua.
  5. Reporte: DAG del contrato, panel de positividad, panel de monitoring, efecto estimado (referencia vs entrada, con IC y sensibilidad) y refutaciones del release.

El orden importa: primero se valida, despues se estima. Se evita explicitamente el antipatron INPUT -> ESTIMATE -> "parece que hubo drift".

Seccion 6

Que se verifica y que no

Por eso la app no muestra un unico CAUSAL VALIDITY = PASS: muestra checks operacionales, supuestos documentados, refutacion, sensibilidad y la lista de supuestos que no se pueden verificar.

CategoriaElementosMecanismo
Comprobable operacionalmente schema, codificacion del tratamiento, rangos, nulos, overlap, propensity extremo, distribution shift, versiones e integridad del artefacto checks que permiten, advierten o bloquean
Evaluable con evidencia indirecta interferencia (SUTVA), sensibilidad a confusion no observada, estabilidad diagnosticos y refutaciones; resultado REVIEW / ROBUST, nunca PASS
No demostrable por una app ignorabilidad verdadera, ausencia absoluta de interferencia, validez causal universal exigen justificacion sustantiva
Limitaciones conocidas.
  • Datos sinteticos: no hay validez externa en juego.
  • Efecto homogeneo bajo PLR: no apto para decisiones individuales ni focalizacion.
  • El KS de monitoring es aproximado (el perfil guarda cuantiles, no la muestra).
  • El valor de robustez se aplica a los residuales del DML y es una aproximacion.
  • Sin base externa, el historial no sobrevive a la sesion.
  • En este escenario el IC contiene el ATE verdadero del simulador (3.97), pero la estimacion puntual lo subestima en ~0.44.
